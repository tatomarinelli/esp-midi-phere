esp-midi-phere — KiCad schematic
=================================

Files:
  esp-midi-phere.kicad_pro   — KiCad project file
  esp-midi-phere.kicad_sch   — the schematic itself

To open: install KiCad (free, kicad.org, v7 or newer), then open the
.kicad_pro file and click the schematic editor icon (or open the .kicad_sch
directly in the Schematic Editor / eeschema).

What's in it
------------
One sheet, all custom symbols (drawn generically — footprints are left
blank since this is a point-to-point wired build, not a PCB):

  U9        ESP32-S3-Zero — full GPIO map, reserved/NC pins marked
  POT1-12   B10K pots, 1-10 on ADC1, 11-12 on ADC2
  RF1-12 / CF1-12   220R / 100nF noise-filter pairs, one per pot
  U1-U6     VU NeoPixel chain (GPIO11), daisy-chained DOUT->DIN
  R1 / C1   300R series resistor + 1000uF bulk cap at the VU chain's entry
  U7        Status NeoPixel stick (GPIO14), 6 of 8 pixels used
  R2 / C2   same 300R/1000uF pair at the status chain's entry
  U8        PCF8574 I2C GPIO expander (GPIO15 SDA, GPIO16 SCL)
  SW1-8     buttons on the PCF8574 — SW1-6 are per-channel IN/AUTO/OFF,
            SW7-8 are page-nav buttons whose function isn't decided yet

Reading the connections
------------------------
Nets that travel across the sheet (GPIO lines, +5V, +3V3, GND, the I2C
bus, button nets) are drawn as a short wire stub ending in a global label
(the flag-shaped text, e.g. "GPIO3") rather than one long wire routed
across the whole page — standard practice once you have a dozen
near-identical repeated sub-circuits: any two global labels with the same
text are the same electrical net, wherever they sit on the sheet. Only
physically adjacent parts (e.g. one NeoPixel stick's DOUT to the next
stick's DIN) are wired directly.

Verification — what was actually done
--------------------------------------
This file was generated by a small Python script writing raw KiCad
S-expression syntax, then verified against a real, locally-installed
KiCad 10.0.4 (kicad-cli) — not just eyeballed:

  1. kicad-cli sch erc: runs cleanly, 0 connectivity errors.
     (3 remaining "power pin not driven" notices are the standard,
     expected complaint for power rails built from labels instead of
     dedicated PWR_FLAG symbols — cosmetic, not a wiring problem.)
  2. kicad-cli sch export netlist: every net's membership was checked
     programmatically against the intended design — e.g. each pot's
     GPIO net contains exactly {filter resistor, filter cap, MCU pin},
     no component has both its own pins shorted onto the same net, the
     two NeoPixel chains terminate cleanly, and all 8 button nets pair
     correctly with their PCF8574 pins.
  3. kicad-cli sch export svg: rendered and visually spot-checked.

Three real bugs were found and fixed this way (left here in case it's
useful context, or you hit something similar hand-authoring KiCad files
yourself):
  - A stub-label direction mistake made two different capacitor pins
    collide at the exact same coordinate, silently shorting GND onto
    +5V/GPIO nets across the whole design.
  - KiCad mirrors a symbol library's internal Y-axis when placing an
    instance on the sheet (library coords are Y-up, the sheet is
    Y-down) — every custom symbol's pin math needed a sign flip to
    account for this. Symmetric 2-pin parts (R, C) masked the bug in
    isolated testing because their two pins just swapped identity and
    still happened to land on real wires; the pot's 3-pin asymmetric
    layout and the PCF8574's 12 distinct pins didn't have that luck.
  - Paper orientation used an unsupported `landscape` keyword that
    made the whole file fail to load; dropped in favor of plain
    `(paper "A1")`.

Given that history, treat this as solid rather than provisional — but if
KiCad still complains on your machine, paste the exact error and it can
be patched fast.
